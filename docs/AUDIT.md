## ۱. باگ‌های واقعی که پیدا و رفع شدند

### باگ ۱ — ذخیره تنظیمات، تب‌های دیگر را خاموش می‌کرد (بحرانی)

**نشانه:** کاربر در «تنظیمات ← واحد پول» مبلغ را عوض می‌کرد و ذخیره می‌زد. بی‌صدا «الزام دلیل ابطال»، «ارقام فارسی»، «پنل خوش‌آمدگویی» و «اجازه حذف شخص» خاموش می‌شدند.

**ریشه:** هر تب فرم جداست و فقط فیلدهای خودش را می‌فرستد. منطق `save()` یک نگهبان داشت (`settings_section`) که هرگز از هیچ فرمی ارسال نمی‌شد، پس همیشه `'all'` بود و چک‌باکس غایب به `0` تبدیل می‌شد.

**رفع:** فرم `active_tab` می‌فرستد و کنترلر آن را به `settings_section` نگاشت می‌کند. متد `section_keys()` هر تب را به کلیدهای خودش محدود می‌کند، پس ذخیره یک تب بقیه را دست نمی‌زند.

```
includes/Core/class-sparkknife-ledger-settings.php    ← section_keys() + محدودسازی دامنه
includes/Admin/Controllers/…-admin-controller.php     ← نگاشت active_tab → settings_section
```

---

### باگ ۲ — گزینه «حذف داده‌ها هنگام حذف افزونه» هرگز اعمال نمی‌شد (بحرانی)

**نشانه:** کاربر گزینه را روشن می‌کرد، افزونه را حذف می‌کرد، و همه داده‌ها باقی می‌ماندند — درست برخلاف انتظار.

**ریشه:** دو منبع برای یک تنظیم وجود داشت. آرایه تنظیمات `1` ذخیره می‌کرد، اما `uninstall.php` شرط `'yes' === get_option(…)` را بررسی می‌کرد و آن گزینه هرگز `'yes'` نمی‌شد.

**رفع:** `Settings::save()` هر دو را هم‌گام می‌کند (`'yes'`/`'no'`).

---

### باگ ۳ — گزارش چاپی زبان غلط اعلام می‌کرد

**نشانه:** یک سند کاملاً فارسی با `<html lang="en-US" dir="rtl">` ساخته می‌شد.

**ریشه:** `language_attributes()` از زبان سایت وردپرس می‌آید، نه از زبان محتوا.

**رفع:** `lang="fa-IR"` صریح. برای صفحه‌خوان، موتور جستجو و shaping فونت فارسی اهمیت دارد.

---

### باگ ۴ — چندسایتی: سایت‌های جدید جداول نمی‌گرفتند

**نشانه:** با فعال‌سازی شبکه‌ای، فقط سایت جاری جداول می‌گرفت. هر سایت جدید در شبکه اولین بازدید را با «جدول یافت نشد» مواجه می‌شد.

**ریشه:** `register_activation_hook` در حالت شبکه فقط یک‌بار و برای سایت جاری اجرا می‌شود.

**رفع:** هوک `wp_initialize_site` برای سایت‌های جدید و `activate_network()` برای همه سایت‌های موجود، با بررسی `$network_wide` تا در تک‌سایتی دوباره نصب نشود.

---

### باگ ۵ — `format_amount()` روی آرایه هشدار PHP می‌داد

**نشانه:** توسعه‌دهنده `sparkknife_ledger_get_balance()` (که خلاصه کامل برمی‌گرداند) را به `format_amount()` می‌داد و به‌جای مانده، `۰ تومان` با یک `Warning: Array to string conversion` می‌گرفت.

**رفع:** بررسی صریح `is_array()` در `Amount::normalize()`.

---

### باگ ۶ — کد جستجوی زنده هرگز اجرا نمی‌شد (کد مرده)

**نشانه:** در `admin.js` یک تابع `initLiveSearch()` وجود داشت که به `#spk-live-search` نگاه می‌کرد. این شناسه در هیچ view وجود نداشت؛ فیلدهای جستجو `spk-person-search` و `spk-search` نام دارند.

**نتیجه:** این قابلیت هیچ‌وقت فعال نمی‌شد.

**بررسی بیشتر:** اگر شناسه‌های واقعی را اضافه می‌کردم، بدتر می‌شد. آن فیلدها بخشی از یک فرم **GET با جستجوی سمت سرور** هستند و نتیجه صفحه‌بندی شده است. جستجوی زنده‌ی سمت کاربر فقط ردیف‌های صفحه جاری را مخفی می‌کند، پس کاربری که «مریم» را جستجو کند و مریم در صفحه ۲ باشد، صفحه خالی می‌بیند.

**رفع:** تابع حذف شد و سرصفحه فایل به‌روز شد. جستجوی سمت سرور موجود است و به‌درستی کار می‌کند.

---

### باگ ۷ — مبلغ منفی از اعتبارسنجی سمت کاربر رد می‌شد

**نشانه:** کاربر `-5` وارد می‌کرد، JS قبول می‌کرد، سرور رد می‌کرد.

**ریشه:** `replace(/[^\d.]/g, '')` علامت منفی را حذف می‌کند، پس `-5` به `5` تبدیل می‌شد و از شرط `<= 0` می‌گذشت.

**رفع:** علامت منفی پیش از پاک‌سازی نویسه‌ها بررسی می‌شود.

> سرور همیشه محافظت می‌کرد؛ این فقط تجربه کاربری بود. ولی پیام خطای متناقض («مبلغ نامعتبر» بعد از اینکه JS قبولش کرد) گیج‌کننده است.

---

### باگ ۸ — کلید تنظیمات ناموجود `admin_rtl`

**نشانه:** `Settings::get( 'admin_rtl', 'rtl' )` خوانده می‌شد ولی این کلید در هیچ‌جای تنظیمات تعریف نشده بود.

**نتیجه:** مقدار پیش‌فرض همیشه برمی‌گشت، پس `isRtl` همیشه `1` بود — که درست است (رابط همیشه راست‌به‌چپ است) اما خواندن یک کلید ناموجود گمراه‌کننده است.

**رفع:** مقدار ثابت `1` با توضیح.

## پاس سوم — بررسی با مرجع مستقل

پاس‌های اول و دوم با خواندن کد انجام شد. پاس سوم با **مقایسه خروجی با مرجع مستقل** انجام شد و ده نقص دیگر پیدا شد.

### باگ ۹ — تقویم شمسی برای ۱۴۵ سال از ۳۰۰ سال، کبیسه را برعکس می‌دانست ⚠️ شدیدترین

**نشانه:** فرم ثبت تراکنش، تاریخ `1403/12/30` (۳۰ اسفند ۱۴۰۳) را با پیام «روز وارد‌شده در این ماه شمسی وجود ندارد» رد می‌کرد — در حالی که ۱۴۰۳ کبیسه است و آن روز واقعاً وجود دارد.

**ریشه:** در `is_jalali_leap()` پیش از گرفتن باقی‌مانده ۳۳، عدد ۱۵۹۵ به سال اضافه می‌شد:

```php
$jy += 1595;                                  // ← اشتباه
$rem = ( ( ( $jy % 33 ) + 3 ) % 33 );
```

چرخه کبیسه شمسی بر **خودِ** سال شمسی اعمال می‌شود. افزودن ۱۵۹۵ باقی‌مانده را کاملاً جابه‌جا می‌کند.

**اندازه فاجعه:** با مقایسه با کتابخانه `jdatetime` روی ۳۰۰ سال، **۱۴۵ سال** کبیسه‌شان برعکس بود. یعنی کاربر نمی‌توانست آخرین روز حدود نیمی از سال‌های کبیسه را ثبت کند، و در سال‌های غیرکبیسه روز ناموجود `30/12` **پذیرفته** می‌شد.

**رفع:** حذف `+1595`. تأیید با مرجع:

| آزمون | پیش از رفع | پس از رفع |
| --- | --- | --- |
| میلادی → شمسی (۱۰۹٬۵۷۳ روز) | ۰ اختلاف | ۰ اختلاف |
| شمسی → میلادی (۱۰۹٬۵۷۳ روز) | **۷۲ اختلاف** | ۰ اختلاف |
| کبیسه بودن ۳۰۰ سال | **۱۴۵ سال غلط** | ۰ |

### باگ ۱۰ — «۱.۲۳۴» هزار برابر کوچک‌تر از خواسته کاربر ذخیره می‌شد

**نشانه:** کاربر مبلغ را `1.234` می‌نویسد (نقطه به‌جای جداکننده هزارگان — عادت رایج با کیبورد عددی). افزونه آن را «یک و ۲۳۴ هزارم» می‌خواند و **۱۲۳۴ تومان را ۱ تومان** ثبت می‌کرد.

**رفع:** الگوی نقطه‌ی درست‌چیده‌شده در گروه‌های سه‌رقمی به‌عنوان جداکننده هزارگان شناسایی می‌شود. اعشار واقعی (`12.5`، `0.75`) دست‌نخورده می‌ماند.

---

### باگ ۱۱ — مبلغ منفی با علامت منفی یونیکد، مثبت ثبت می‌شد

**نشانه:** کاربر `−۵` را با علامت منفی یونیکد (U+2212) می‌فرستد — که کیبوردهای فارسی و کپی از وب تولید می‌کنند. `Sanitizer::amount()` آن را به‌عنوان «نویسه غیرمجاز» حذف می‌کرد و `۵` می‌ماند، سپس به‌عنوان مبلغ مثبت معتبر ثبت می‌شد.

**رفع:** منفی‌های یونیکد (U+2212، U+2013، U+2014، U+FE63) پیش از پاک‌سازی به منفی ASCII تبدیل می‌شوند.

---

### باگ ۱۲ — خطای مرگبار در فرم ویرایش تراکنش (صفحه سفید)

**نشانه:** در `transactions/form.php`:

```php
Money::format( Money::parse_amount( $values['amount'] ) ?: 0 )
```

`parse_amount()` در خطا `WP_Error` برمی‌گرداند و `WP_Error` در شرط بولی **صدق‌پذیر** است. پس `?: 0` هرگز به `۰` نمی‌رسید و `format()` روی شیء خطا با `Object of class WP_Error could not be converted to string` منفجر می‌شد.

**رفع:** بررسی `is_string()` به‌جای `?:`. همچنین `format()` خودش شیء و آرایه را با خط تیره پاسخ می‌دهد تا این کلاس خطا دیگر تکرار نشود.

---

### باگ ۱۳ — خطای مرگبار در خروجی CSV با داده ناقص

**نشانه:** `person_report_rows()` یک متد عمومی است. اگر کلیدهای `person`/`range`/`summary` در آرایه ورودی نبودند، به `TypeError` می‌رسید.

**رفع:** بازگشت امن با پیام فارسی + helper برای خواندن ایمن کلیدهای خلاصه.

---

### باگ ۱۴ — هر خطای اعتبارسنجی **دو بار** به کاربر نشان داده می‌شد

**نشانه:** `flash_error()` هم ترنزینت `form_errors` را ست می‌کرد (که `header.php` نمایش می‌دهد) و هم `add_notice()` را صدا می‌زد (که از قلاب `admin_notices` نمایش می‌یابد). هر دو مسیر فعال بودند.

**رفع:** `flash_error()` دیگر `add_notice` صدا نمی‌زند؛ فراخوان‌ها خودشان `add_notice( ..., $redirect )` را دارند.

---

### باگ ۱۵ — جعبه خطای توخالی در صفحه فرم

**نشانه:** `redirect_back_with()` اعلانی با **پیام خالی** ثبت می‌کند تا فقط کاربر به فرم برگردد. `render_admin_notices()` پیام خالی را بررسی نمی‌کرد و یک `<div class="notice notice-error"><p></p></div>` توخالی چاپ می‌کرد.

**رفع:** پیام خالی رندر نمی‌شود.

---

### باگ ۱۶ — حذف همه داده‌ها به `exit` داخلی یک تابع تکیه داشت

**نشانه:** در `handle_data_purge()`:

```php
if ( ! current_user_can( 'manage_options' ) ) {
    add_notice( ... );   // ← فقط اعلان، بدون return
}
if ( 'DELETE-ALL-DATA' !== $confirm ) {
    add_notice( ... );   // ← فقط اعلان، بدون return
}
Installer::purge_all_data();   // ← اجرا می‌شد
```

امروز امن است چون `add_notice` با `$redirect` غیرخالی `exit` می‌کند. ولی محافظت یک عملیات **نابودکننده** به یک عارضه جانبی در تابع دیگر وابسته بود. اگر روزی `add_notice` تغییر می‌کرد یا `$redirect` خالی می‌شد، حذف داده برای کاربر بی‌مجوز اجرا می‌شد.

**رفع:** هر دو شرط `return` صریح دارند.

---

### باگ ۱۷ — uninstall در حالت «حذف کامل»، دو آپشن را جا می‌گذاشت

**نشانه:** شاخه حذف کامل پیش از پاک‌سازی `sparkknife_ledger_db_version` و `sparkknife_ledger_version` `return` می‌کرد. نتیجه: هزاران بازدید بعد، این دو آپشن باقی می‌ماندند و **نصب مجدد فکر می‌کرد جداول هنوز وجود دارند** و مهاجرت را رد می‌کرد.

**رفع:** پاک‌سازی نسخه به هر دو شاخه منتقل شد. آزمون: صفر آپشن باقی‌مانده با پیشوند `sparkknife`.

---

### باگ ۱۸ — نمایش تاریخ روی PHP ۳۲ بیتی

**نشانه:** `strtotime()` روی PHP ۳۲ بیتی برای سال‌های دور از محدوده `int` هشدار `Epoch doesn't fit in a PHP integer` می‌دهد و `false` برمی‌گرداند، پس `Date::format()` خط تیره نشان می‌داد. اعتبارسنج تاریخ سال‌های ۱۹۰۰ تا ۲۲۰۰ را می‌پذیرد، یعنی کاربر می‌توانست تراکنشی با تاریخ ۱۹۰۰ ثبت کند و بعد هیچ تاریخی نبیند.

**رفع:** تجزیه با regex و `checkdate()` جای `strtotime()` را گرفت — بدون هیچ محاسبه‌ای روی epoch.

| تاریخ | پیش از رفع | پس از رفع | مرجع |
| --- | --- | --- | --- |
| 1900-01-01 | `—` + هشدار | ۱۲۷۸/۱۰/۱۱ | ۱۲۷۸/۱۰/۱۱ ✓ |
| 2199-12-31 | `—` + هشدار | ۱۵۷۸/۱۰/۱۰ | ۱۵۷۸/۱۰/۱۰ ✓ |

---

### باگ ۱۹ — ترتیب ناپایدار در گزارش تجمیعی روی PHP ۷.۴

**نشانه:** `usort()` پیش از PHP ۸.۰ پایدار نیست. ردیف‌هایی با مانده یکسان می‌توانستند بین صفحه‌ها **جابه‌جا یا تکرار** شوند. افزونه PHP 7.4 را پشتیبانی می‌کند.

**رفع:** کلید دوم (`id`) برای شکستن تساوی.

## پاس چهارم — عمق عملیاتی

پاس‌های قبلی روی درستی منطق و امنیت تمرکز داشتند. این پاس مسیرهایی را
بررسی کرد که فقط در استفاده واقعی و زیر بار ظاهر می‌شوند: صادرات کامل،
همزمانی، بازیابی پس از خرابی، و سازگاری با هاست‌های ضعیف‌تر.

### باگ ۲۰ — جستجوی فارسی نویسه‌به‌نویسه بود (بحرانی)

**نشانه:** کاربر «علي» را تایپ می‌کرد و شخصی که با نام «علی» ذخیره شده
بود پیدا نمی‌شد. هیچ خطایی هم نبود؛ فقط «نتیجه‌ای یافت نشد».

**علت:** `LIKE` در MySQL مقایسه بایتی می‌کند. «ی» فارسی
(`U+06CC`) و «ي» عربی (`U+064A`) دو بایت متفاوت‌اند، پس الگو مطابقت
نمی‌کرد. همین برای «ک/ك»، «ه/ة» و ارقام فارسی/عربی هم بود.

**رفع:** `Sanitizer::search_variants()` همه ترکیب‌های ممکن را می‌سازد و
مخازن با `OR` روی آن‌ها جستجو می‌کنند. تست: ۷ شکل املا، همه ۱ نتیجه.

### باگ ۲۱ — فهرست اشخاص با `strcmp()` مرتب می‌شد (متوسط)

**نشانه:** در فهرست، «پرویز» پیش از «تیرداد» می‌آمد.

**علت:** `strcmp()` ترتیب بایتی UTF-8 می‌دهد. در UTF-8 حرف «پ» بایت
بالاتری از «ت» دارد، ولی در الفبای فارسی بعد از «ت» می‌آید.

**رفع:** `Sanitizer::persian_sort_key()` هر نویسه را به یک بایت قابل
مقایسه تبدیل می‌کند. تست: ۱۰ نام، ترتیب الفبایی درست.

### باگ ۲۲ — شماره تلفن با ارقام فارسی پیدا نمی‌شد (متوسط)

**نشانه:** جستجوی «۰۹۱۲» هیچ نتیجه‌ای نداشت، ولی «0912» کار می‌کرد.

**علت:** کیبورد فارسی ارقام فارسی (`U+06F0`–`U+06F9`) تولید می‌کند ولی
شماره‌ها با ارقام لاتین ذخیره می‌شوند.

**رفع:** ارقام فارسی و عربی پیش از مقایسه به لاتین تبدیل می‌شوند.

### باگ ۲۳ — `maybe_upgrade()` جداول حذف‌شده را ترمیم نمی‌کرد (بحرانی)

**نشانه:** اگر جداول به‌دست کاربر یا افزونه دیگری حذف می‌شد، پنل خطای
دیتابیس می‌داد و هیچ راهی برای ترمیم از داخل افزونه نبود.

**علت:** تابع اگر `db_version` برابر نسخه جاری بود، بلافاصله `return`
می‌کرد — بدون آنکه بررسی کند جداول هنوز وجود دارند.

**رفع:** حالا وجود جداول هم بررسی می‌شود؛ اگر نسخه درست ولی جدول‌ها غایب
باشند، `create_tables()` و نصب پیش‌فرض‌ها اجرا می‌شوند.

### باگ ۲۴ — نقطه در ارز اعشاری جداکننده هزارگان شمرده می‌شد (بحرانی)

**نشانه:** با واحد پول دلار، مبلغ `1.500` به‌جای ۱.۵ دلار، **۱۵۰۰
دلار** ثبت می‌شد.

**علت:** پاس سوم قاعده‌ای اضافه کرده بود که «۱.۲۳۴» را ۱۲۳۴ می‌خواند،
چون کاربران ایرانی نقطه را به‌جای جداکننده هزارگان می‌نویسند. آن قاعده
بی‌قید اجرا می‌شد و برای ارزهای اعشاری غلط بود.

**رفع:** قاعده فقط وقتی اعمال می‌شود که ارز صفر رقم اعشار داشته باشد.
تومان: `1.500` = ۱۵۰۰. دلار: `1.500` = ۱.۵.

### باگ ۲۵ — صادرات CSV و چاپ، بی‌صدا ناقص بودند (بحرانی)

**نشانه:** با ۲۵۰ شخص، فایل CSV فقط **۲۰ ردیف** و گزارش چاپی فقط
**۲۰۰ ردیف** داشت. ستون «جمع کل» اما ۲۵۰ را نشان می‌داد.
برای یک دفتر مالی این یعنی آرشیو ناقص از داده مالی.

**علت:** دو عدد ناهماهنگ. کنترلر چاپ `per_page = 500` می‌فرستاد و
هر دو متد گزارش آن را بی‌صدا به ۲۰۰ کاهش می‌دادند. کنترلر CSV اصلاً
عددی نمی‌فرستاد، پس روی پیش‌فرض سایت (۲۰) می‌ماند.

**رفع:** هر دو متد پرچم `for_export` می‌گیرند که سقف را به ۱۰۰٬۰۰۰
می‌رساند و هر دو کنترلر آن را می‌فرستند. سقف ۲۰۰ برای صفحه‌های عادی
سر جایش است. تست: ۴۵ تراکنش شخص، همه در خروجی.

### باگ ۲۶ — جستجو در گزارش تجمیعی هم نویسه‌به‌نویسه بود (متوسط)

**نشانه:** «علي» در فهرست اشخاص نتیجه می‌داد ولی در گزارش تجمیعی نه.

**علت:** باگ ۲۰ مخازن را رفع کرد، اما گزارش تجمیعی در PHP و با کد
خودش فیلتر می‌کرد. آن مسیر جا مانده بود.

**رفع:** هر دو طرف مقایسه با `normalize_persian()` یکسان می‌شوند.

### باگ ۲۷ — `mb_stripos()` بدون محافظ (متوسط)

**نشانه:** روی هاستی بدون افزونه `mbstring`، باز کردن گزارش یا ثبت
تراکنش با **صفحه سفید** تمام می‌شد.

**علت:** `mbstring` افزونه اختیاری PHP است. دو جا بدون بررسی
`function_exists` صدایش می‌زدند.

**رفع:** گزارش به `stripos` منتقل شد و سرویس تراکنش از
`Sanitizer::limit()` استفاده می‌کند که خودش محافظ دارد.

### باگ ۲۸ — تاریخ بعد از ۲۰۳۸ «آینده» شمرده نمی‌شد (متوسط)

**نشانه:** می‌شد تراکنشی با تاریخ ۲۰۴۰ یا ۲۰۹۹ ثبت کرد، بدون هیچ
خطا و هیچ هشداری.

**علت:** روی PHP ۳۲ بیتی `strtotime()` برای تاریخ بعد از ۱۹ ژانویه ۲۰۳۸
مقدار `false` می‌دهد، و `false > int` همیشه نادرست است. پس بررسی
«تاریخ نمی‌تواند در آینده باشد» بی‌صدا از کار می‌افتاد.

**رفع:** `Date::is_future()` دو رشته `Y-m-d` را مستقیم مقایسه می‌کند؛
قالب با طول ثابت، ترتیب لغوی درستی دارد و اصلاً حساب epoch لازم نیست.
تست: ۲۰۴۰ و ۲۰۹۹ رد می‌شوند، فردا هنوز مجاز است، هر دو تقویم.

### باگ ۲۹ — نام کاملاً نامرئی پذیرفته می‌شد (متوسط)

**نشانه:** می‌شد شخصی با نامی ساخت که هیچ‌چیز نمایش نمی‌داد؛ در فهرست
یک ردیف خالی می‌آمد که نه قابل تشخیص بود نه قابل جستجو.

**علت:** `sanitize_text_field()` بایت null را حذف می‌کند ولی بقیه
نویسه‌های کنترلی C0 و نویسه‌های بی‌عرض مثل نیم‌فاصله را نگه می‌دارد.
اعتبارسنجی «الزامی» هم چون رشته خالی نبود عبور می‌داد.

**رفع:** `Sanitizer::strip_invisible()` کنترل‌ها را حذف می‌کند و اگر
هیچ نویسه دیدنی نماند رشته خالی برمی‌گرداند. نیم‌فاصله داخل نام سالم
می‌ماند («می‌رود» دست‌نخورده است).

### باگ ۳۰ — نام بلند بی‌صدا بریده می‌شد (جزئی)

**نشانه:** نام ۵۰۰ نویسه‌ای به ۱۹۰ نویسه کاهش می‌یافت و ذخیره می‌شد،
بدون هیچ پیامی.

**علت:** `Sanitizer::text()` قبل از اعتبارسنجی برش می‌زد، پس طول اصلی
هرگز سنجیده نمی‌شد.

**رفع:** طول پیش از برش سنجیده می‌شود و پیام صریح می‌دهد. ضمناً
`Sanitizer::length()` اضافه شد که بدون `mbstring` هم نویسه می‌شمارد؛
قبلاً قاعده «حداقل دو نویسه» روی هاست بدون `mbstring` کار نمی‌کرد.

### چه چیزهایی در این پاس سالم بودند

این موارد بررسی شدند و مشکلی نداشتند — ثبت می‌شوند تا در پاس‌های بعد
دوباره بررسی نشوند:

| مورد | نتیجه |
| --- | --- |
| تزریق CSV (`=1+1` در نام) | `sanitize_cell()` هر سلول را با `'` خنثی می‌کند |
| تزریق `orderby` در SQL | فهرست مجاز + `ASC/DESC` ثابت |
| باز-ریدایرکت پس از ذخیره | فقط نشانی‌های پنل همین سایت |
| Nonce و دسترسی هر سه نقطه ورود | بررسی‌شده، هر handler دسترسی خودش را دارد |
| فیلد ناشناخته در فرم تنظیمات | نادیده گرفته می‌شود؛ هر کلید صریح اعتبارسنجی می‌شود |
| میانگین مبالغ | `ROUND(AVG())` روی مقیاس ۴ درست است |
| حذف شخص دارای تراکنش | رد می‌شود با راهنمایی «غیرفعال کنید» |
| حذف و بازیابی شخص بدون تراکنش | گزارش و داشبورد هم‌زمان درست به‌روز می‌شوند |

| کارایی: ۵۰ شخص / ۲۰۰۰ تراکنش | گزارش تجمیعی ۳۳ms، گزارش فردی ۱۷ms، درج ۱.۶ms |

## پاس پنجم — تقویم در گزارش‌ها و یکپارچگی اعداد

پاس چهارم روی صادرات، همزمانی و بازیابی تمرکز داشت. این پاس یک لایه
بالاتر رفت و پرسید: آیا اعدادی که کاربر می‌بیند، همان چیزی هستند که
منطقاً باید باشند؟ و آیا تقویم شمسی در همه گزارش‌ها یکسان رعایت می‌شود؟

### باگ ۳۱ — «این ماه» یک ماه شمسی نبود (بحرانی)

**نشانه:** در تقویم شمسی، دکمه «این ماه» بازه‌ای می‌داد که نه با ماه
شمسی شروع می‌شد نه تمام می‌شد.

**علت:** بازه‌های آماده با `gmdate` میلادی حساب می‌شدند. در ۱۲ آبان ۱۴۰۵
(۲۰۲۶-۱۱-۰۳)، «این ماه» می‌شد ۱ تا ۳۰ نوامبر، که در شمسی است **۱۰ آبان
تا ۹ آذر**. یعنی نُه روز اول آبان گم می‌شد و نُه روز از آذر بی‌ربط
اضافه می‌شد. «سال جاری» تقویم را درست رعایت می‌کرد، پس دو بازه با هم
ناسازگار بودند.

**رفع:** بازه‌ها از تقویم فعال ساخته می‌شوند. طول ماه‌های شمسی (۳۱ روز
برای شش ماه اول، ۳۰ برای پنج ماه بعد، ۲۹ یا ۳۰ برای اسفند) به تاریخ
میلادی ذخیره‌سازی نگاشت می‌شوند. تست: هر ۱۲ ماه ۱۴۰۵ بدون شکاف و
همپوشانی، و ۱۴۰۳ به‌عنوان سال کبیسه.

**نکته:** تست قدیمی این باگ را تثبیت کرده بود؛ همیشه تاریخ میلادی را
انتظار داشت. آن هم اصلاح شد.

### باگ ۳۲ — نمودار ماهانه ماه‌ها را جابه‌جا نشان می‌داد (بحرانی)

**نشانه:** تراکنش ۵ آذر در ستون **آبان** دیده می‌شد و ستون آذر اصلاً
وجود نداشت.

**علت:** گروه‌بندی با `DATE_FORMAT(txn_date, '%Y-%m')` میلادی بود. ۵ آذر
می‌شود ۲۰۲۶-۱۱-۲۶ که در سطل «2026-11» می‌افتد، و آن سطل برچسب شمسی
آبان می‌گرفت. برچسب هم از `Date::format( key . '-01' )` ساخته می‌شد که
«۱۴۰۵/۰۸/۱۰» می‌داد — دهم ماه، نه نام ماه.

**رفع:** گروه‌بندی در PHP و بر اساس مرزهای ماه شمسی. هر سطل برچسب،
شروع و پایان خودش را دارد («آبان ۱۴۰۵»).

### باگ ۳۳ — جمع زیر جدول با ستون‌هایش نمی‌خواند (بحرانی)

**نشانه:** با دو شخص ۱٬۰۰۰ و ۹٬۰۰۰ تومانی، جستجوی اولی یک ردیف
۱٬۰۰۰ تومانی نشان می‌داد و «جمع کل» زیر جدول **۱۰٬۰۰۰**.

**علت:** `totals` عمداً مستقل از جستجو و از کل بازه حساب می‌شود — کارت‌های
بالای صفحه برچسب «مجموع ... تمام اشخاص» دارند و درست است. اما همان عدد
در `<tfoot>` جدول هم استفاده می‌شد، یعنی زیر ستون‌هایی که فقط ردیف‌های
فیلترشده را نشان می‌دادند.

**رفع:** گزارش حالا `filtered_totals` هم برمی‌گرداند — جمع همان ردیف‌هایی
که نمایش داده می‌شوند. جدول، چاپ و CSV از آن استفاده می‌کنند. کارت‌ها
جمع کل را نگه می‌دارند. در CSV که فقط ردیف‌های فیلترشده هست، هر دو عدد
با برچسب صریح نوشته می‌شوند.

### باگ ۳۴ — تب تنظیمات ناشناخته همه چک‌باکس‌ها را خاموش می‌کرد (بحرانی)

**نشانه:** ارسال `settings_section` با نامی که در نقشه نیست، تمام تنظیمات
بولی را خاموش می‌کرد: ارقام فارسی، الزام دلیل ابطال، اجازه حذف شخص.

**علت:** `section_keys()` برای نام ناشناخته آرایه خالی برمی‌گرداند و شرط
`! empty( $section_keys )` محافظت را رد می‌کرد. پس `$sanitized` دست‌نخورده
می‌ماند و همه چک‌باکس‌ها صفر می‌شدند. این همان باگ پاس اول بود، از راه
دیگری.

**رفع:** تب ناشناخته `WP_Error` برمی‌گرداند و **هیچ چیز** نوشته نمی‌شود.
کنترلر هم خطا را نشان می‌دهد؛ پیش‌تر پیام «تنظیمات با موفقیت ذخیره شد»
بی‌قید نمایش داده می‌شد و حتی وقتی چیزی نوشته نمی‌شد موفقیت اعلام می‌کرد.

### باگ ۳۵ — IP لاگ ممیزی قابل جعل بود (امنیتی)

**نشانه:** هر کاربری می‌توانست با فرستادن هدر `X-Forwarded-For` هر IP
دلخواهی را در لاگ ممیزی ثبت کند.

**علت:** هدر پروکسی **همیشه** بر `REMOTE_ADDR` اولویت داشت، و از **چپ‌ترین**
عضو زنجیره خوانده می‌شد — همان بخشی که خود کلاینت می‌نویسد. پروکسی واقعی
آدرس را به **انتها** اضافه می‌کند.

**رفع:** هدر به‌طور پیش‌فرض نادیده گرفته می‌شود. برای سایت پشت پروکسی،
`define( 'SPARKKNIFE_LEDGER_TRUST_PROXY', true )` یا فیلتر
`sparkknife_ledger_trust_proxy`. در آن حالت **راست‌ترین** آدرس معتبر
استفاده می‌شود. در دفتر مالی، IP ابزار ردیابی است؛ اگر جعل‌شدنی باشد،
ارزش اثباتی لاگ از بین می‌رود.

### باگ ۳۶ — برش متن وسط نویسه UTF-8 (متوسط)

**نشانه:** رشته خراب در لاگ و JSON نامعتبر.

**علت:** `substr()` بایت می‌شمارد. روی ایموجی یا متن فارسی سقف ۲۵۵ بایتی
وسط یک نویسه می‌افتد و بایت‌های ناقص می‌ماند. `User-Agent` هم ورودی
کاربر است و می‌تواند هر چیزی باشد.

**رفع:** همه برش‌ها از `Sanitizer::limit()` عبور می‌کنند که نویسه‌ای
می‌برد. `limit()` خودش هم در شاخه بدون `mbstring` از `substr` استفاده
می‌کرد که اصلاح شد. تست: ایموجی، متن مختلط و ۵۰۰ نویسه فارسی، همه
خروجی UTF-8 سالم.

### چه چیزهایی در این پاس سالم بودند

| مورد | نتیجه |
| --- | --- |
| `Date::format()` با ورودی نامعتبر | همه به «—» تبدیل می‌شوند، بدون Warning |
| مرز «امروز» در بازه‌ها | تراکنش امروز در همه بازه‌های مربوط می‌آید |
| حذف جدول ممیزی | تراکنش ثبت می‌شود و کار متوقف نمی‌شود (تصمیم درست) |
| برچسب کارت‌های گزارش | «مجموع ... تمام اشخاص» صریح است، گمراه‌کننده نیست |
| گزارش فردی با فیلتر نوع | کارت‌ها کل، بخش فیلترشده جداگانه |
| فراخوانی‌های `Settings::save()` | همه مقدار برگشتی را چک می‌کنند |
| کوئری نمودار جدید | `$wpdb->prepare` با `%s`، بدون تزریق |

## ۲. موارد بررسی‌شده و سالم

### امنیت

| بررسی | نتیجه |
| --- | --- |
| SQL Injection | ✅ نام ستون‌های `ORDER BY` از whitelist (`sortable_columns()`), تمام مقادیر با `prepare()` |
| XSS | ✅ همه خروجی‌ها با `esc_html`/`esc_attr`/`esc_url`؛ شرطی‌های ثابت در کلاس‌ها |
| CSRF | ✅ `check_admin_referer` در همه‌ی ۹ handler، nonce اختصاصی هر action |

| بارگذاری مستقیم فایل | ✅ همه فایل‌ها `ABSPATH`-guard دارند |
| `uninstall.php` | ✅ فقط با `WP_UNINSTALL_PLUGIN` اجرا می‌شود |
| XSS در چاپ | ✅ تست شد؛ `<script>` در توضیحات به چاپ نشت نمی‌کند |
| JS | ✅ `innerHTML`/`document.write` استفاده نمی‌شود |

## ۳. نکات عملیاتی برای نصب

1. **پشتیبان بگیرید:** `wp db export backup.sql`
2. **PHP نسخه ۷.۴ یا بالاتر** — تست‌شده روی 8.2
3. **حذف افزونه:** به‌صورت پیش‌فرض داده‌ها می‌مانند. برای پاک‌سازی، «تنظیمات ← داده‌ها ← حذف داده‌ها هنگام حذف افزونه» را روشن کنید
4. **چندسایتی:** حالا سایت‌های جدید خودکار جداول می‌گیرند
5. **پس از نصب:** «دفتر حساب ← تنظیمات» را یک‌بار مرور و واحد پول/تقویم را تنظیم کنید

## ۴. محدودیت‌های شناخته‌شده

| مورد | وضعیت |
| --- | --- |
| تست روی MySQL واقعی | فقط SQLite drop-in در دسترس بود؛ SQL مطابق استاندارد MySQL نوشته شده |
| مرورگر | بدون دسترسی به مرورگر؛ رندر HTML به‌صورت CLI تست شد |
| ترجمه | فایل `.pot` نداریم؛ ۴۸۶ رشته آماده ترجمه است |
| xlsx واقعی | CSV با BOM (سازگار با Excel)؛ هوک `sparkknife_ledger_export_formats` برای افزودن |
| نوشتن همزمان در SQLite | با ۴ نویسنده موازی، درایور SQLite خطای «database disk image is malformed» می‌دهد. این محدودیت محیط آزمون است، نه افزونه؛ MySQL نوشتن همزمان را مدیریت می‌کند و مسیرهای تک‌نویسنده درست کار می‌کنند |
| `EXPLAIN` و `PRAGMA integrity_check` | درایور SQLite این دستورها را رد می‌کند، پس برنامه اجرای کوئری بررسی نشد؛ ایندکس‌ها به‌صورت ایستا بازبینی شدند |
| سایت پشت پروکسی | IP واقعی کاربر فقط با فعال‌سازی `SPARKKNIFE_LEDGER_TRUST_PROXY` از هدر خوانده می‌شود. بدون آن، IP پروکسی ثبت می‌شود (امن‌تر، ولی کم‌دقت‌تر) |

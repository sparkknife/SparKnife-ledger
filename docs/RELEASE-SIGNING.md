# امضای دیجیتال انتشار

هر بستهٔ SparKnife Ledger که برای فروش منتشر می‌شود باید امضای دیجیتال
داشته باشد. این سند می‌گوید چرا، چطور، و خریدار چطور بررسی‌اش می‌کند.

> جایگزین `SparKnife` را در سراسر این فایل با نام برند خودتان عوض کنید.

---

## چرا امضا

بدون امضا، خریدار هیچ راهی ندارد بداند فایل ZIP که دانلود کرده:

- همان چیزی است که شما فرستاده‌اید، نه نسخهٔ دست‌کاری‌شدهٔ یک واسطه
- در مسیر دانلود با بدافزار ترکیب نشده
- نسخهٔ رسمی است، نه یک فورک با نام شما

امضای دیجیتال این را اثبات می‌کند. بدون آن، اعتماد به «سایت رسمی»
تکیه دارد؛ با آن، اعتماد به ریاضیات.

---

## دو لایه، یک اعتماد

این پروژه دو چیز را با **یک** جفت کلید انجام می‌دهد:

| کاربرد | ابزار | چه چیزی امضا می‌شود |
| --- | --- | --- |
| لایسنس مشتری | `tools/licensing/issue.php` | payload لایسنس |
| بستهٔ انتشار | `tools/sign-release.sh` | چکسام SHA-256 فایل ZIP |

چون هر دو از یک کلید استفاده می‌کنند، خریدار همان کلید عمومی‌ای را که
برای بررسی لایسنس دارد، برای بررسی بسته هم به کار می‌برد. یک ریشهٔ
اعتماد، دو کاربرد.

کلید عمومی از قبل داخل افزونه embed شده است:
`tools/licensing/public_key.pem`

---

## ⚠️ وضعیت فعلی در این مخزن

کلید خصوصی (`tools/licensing/private_key.pem`) در این محیط **وجود
ندارد** — با بازنشانی محیط پاک شد. یعنی:

- بسته هنوز امضای واقعی ندارد
- نمی‌توان برای مشتری لایسنس صادر کرد

**قبل از اولین فروش** این دو کار لازم است:

```bash
cd tools/licensing
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out private_key.pem
openssl rsa -in private_key.pem -pubout -out public_key.pem
```

سپس کلید عمومی تازه را در `includes/Core/class-sparkknife-ledger-license.php`
جایگزین کنید و بیلد تازه بسازید. **بعد** از آن:

- کلید خصوصی را در گاوصندوق رمز بگذارید
- نسخهٔ پشتیبان جداگانه بگیرید
- بسته را با `tools/sign-release.sh` امضا کنید

جزئیات کامل در [`tools/licensing/README.md`](../tools/licensing/README.md).

> اگر با کلید تازه امضا کنید ولی کلید عمومی داخل کد را عوض نکنید،
> هیچ لایسنسی کار نمی‌کند و صفحهٔ سلامت خطا می‌دهد. هر دو با هم.

## مسیر انتشار

### ۱) ساخت بسته

```bash
cd /path/to/repo
zip -r sparkknife-ledger.zip sparkknife-ledger \
  -x '*.DS_Store' -x '__MACOSX/*' -x '*/node_modules/*'
```

بسته باید فقط پوشهٔ `sparkknife-ledger/` را در ریشه داشته باشد — نه
`docs/`، نه `tests/`، نه کلید خصوصی.

### ۲) امضا

```bash
./tools/sign-release.sh sparkknife-ledger.zip
```

خروجی سه فایل است:

```
sparkknife-ledger.zip       بسته
sparkknife-ledger.sha256    چکسام SHA-256
sparkknife-ledger.sig       امضای RSA
```

اگر کلید خصوصی جای دیگری است:

```bash
SPK_PRIVATE_KEY=/secure/path/private_key.pem \
  ./tools/sign-release.sh sparkknife-ledger.zip
```

### ۳) بررسی پیش از انتشار

**همیشه** پیش از انتشار بررسی کنید. یک بستهٔ امضاشده با کلید اشتباه
بدتر از بستهٔ بی‌امضاست، چون اعتماد را خرج می‌کند:

```bash
./tools/verify-release.sh sparkknife-ledger.zip
```

باید ببینید:

```
✓ چکسام SHA-256 مطابق است
✓ امضای RSA معتبر است
نتیجه: بسته معتبر است ✓
```

### ۴) انتشار

هر سه فایل را با هم منتشر کنید. اگر فقط ZIP را بگذارید، امضا بی‌فایده
است.

چکسام را روی صفحهٔ دانلود هم بنویسید:

```
SHA-256: 583bea898f970f31381bcd3d39c3a2b07997d59355c8d1aadcb7d3477a6d2966
```

## خریدار چطور بررسی می‌کند

سه راه، از ساده به پیشرفته.

### الف) سایت، خودش بررسی می‌کند

افزونه صفحهٔ «سلامت و امنیت» دارد که یکپارچگی فایل‌ها را می‌سنجد.
خریدار بعد از نصب همان صفحه را باز می‌کند و اگر فایلی عوض شده باشد
می‌بیند.

### ب) بررسی با ابزار

```bash
./tools/verify-release.sh sparkknife-ledger.zip public_key.pem
```

خروج صفر یعنی معتبر. اگر کد خروج یک بود، بسته را نصب نکنید.

### ج) بررسی دستی

```bash
# چکسام
sha256sum sparkknife-ledger.zip
# با مقدار داخل .sha256 مقایسه کنید

# امضا
openssl dgst -sha256 -verify public_key.pem \
  -signature sparkknife-ledger.sig \
  sparkknife-ledger.zip
# باید بگوید: Verified OK
```

## آنچه امضا اثبات می‌کند — و آنچه نمی‌کند

**اثبات می‌کند:** بسته همان است که با کلید خصوصی SparKnife امضا شده،
و از لحظهٔ امضا یک بایت هم عوض نشده.

**اثبات نمی‌کند:** اینکه اینکه کد باگ ندارد، امن است، یا به آنچه ادعا
می‌کند عمل می‌کند. برای آنها آزمون ۹۶۶ assertion و گزارش
[`AUDIT.md`](AUDIT.md) است.

امضا **نویسنده را هم اثبات نمی‌کند** مگر اینکه کلید عمومی از راه
مستقل به خریدار رسیده باشد. اگر خریدار کلید عمومی را از همان جایی
گرفت که بسته را، یک مهاجم می‌توانست هر دو را عوض کند. پس کلید عمومی
را در چند جای مستقل منتشر کنید: داخل افزونه، در مخزن گیت‌هاب، و روی
صفحهٔ فروش.

## نگهداری کلید

| قاعده | چرا |
| --- | --- |
| کلید خصوصی هرگز در گیت نباشد | `.gitignore` آن را می‌بندد؛ این را بررسی کنید |
| کلید خصوصی هرگز در بستهٔ ZIP نباشد | اسکریپت انتشار باید آن را رد کند |
| یک نسخه در گاوصندوق رمز | گم شدنش همهٔ امضاهای قبلی را بی‌اعتبار می‌کند |
| یک نسخهٔ پشتیبان جدا از لپ‌تاپ کاری | دیسک می‌میرد، لپ‌تاپ گم می‌شود |

**اگر کلید خصوصی گم شود:** همهٔ لایسنس‌های صادرشده باطل می‌شوند و
همهٔ امضاهای قبلی قابل بررسی نیستند. باید جفت کلید تازه بسازید، کلید
عمومی را در افزونه عوض کنید، نسخهٔ تازه با شمارهٔ بالاتر منتشر کنید، و
برای همهٔ مشتریان لایسنس تازه صادر کنید. این یک بار در پاس ۱۱ رخ داد
(باگ ۷۹ در [`AUDIT.md`](AUDIT.md)) — بدون اینکه هیچ تستی شکست بخورد.

## اگر gpg دارید

این پروژه عمداً از `openssl` استفاده می‌کند نه `gpg`، چون:

- کلید عمومی RSA از قبل برای لایسنس وجود دارد
- `openssl` روی هر سروری هست، `gpg` نه
- خروجی را خریدار با یک دستور بررسی می‌کند، بدون کلیدرینگ

اگر gpg را ترجیح می‌دهید، می‌توانید **در کنار** این روش امضای gpg هم
بسازید. ولی جایگزینش نکنید — خریدار باید یک مسیر ساده برای بررسی
داشته باشد.

## فایل‌های امضا در مخزن

`*.sig` و `*.sha256` در `.gitignore` هستند. این درست است: امضا مربوط
به یک **بيلد مشخص** است، نه به کد منبع. هر انتشار امضای خودش را دارد و
باید کنار همان ZIP بماند، نه در مخزن.

اگر می‌خواهید امضاها را برای مشتری آرشیو کنید، در Release گیت‌هاب
پیوستشان کنید:

```bash
gh release create v1.1.0 \
  sparkknife-ledger.zip \
  sparkknife-ledger.sha256 \
  sparkknife-ledger.sig \
  --title "SparKnife Ledger 1.1.0" \
  --notes-file CHANGELOG-1.1.0.md
```
